02 / 独立应用原型 · 酒旅服务

EES 民宿酒店
客户服务 Agent

从民宿与酒店一线服务问题出发，构建一个能够理解住客意图、区分知识与订单权限、管理多轮任务，并在确认后创建可追踪服务工单的 AI 客服原型。

当前版本MVP 1.9
产品形态对话式服务 Agent 原型
核心链路识别 · 核实 · 确认 · 建单
技术栈Python · Streamlit · SQLite · 可选 LLM
STAR / 项目概览

把“能回答问题”升级为“能安全推进服务任务”。

S · Situation

业务情境

民宿 / 酒店线上客服大量依赖人工文字回复。问题表面相似，背后可能涉及门店政策、个人订单、实时房态、现场服务、投诉或退款；不同问题需要不同数据来源、权限和处理路径。

T · Task

产品任务

设计一个具备业务判断能力的服务助手：回答有依据，个人订单先认证，跨轮对话不丢失任务状态，需人工处理的事项能够在住客确认后形成可追踪工单。

A · Action

关键行动

逐步构建 RAG、规则与可选 LLM 混合路由、演示身份与订单只读服务、多订单上下文管理、对话式建单、工单分类与状态流转，并用合成场景和自动化测试迭代。

R · Result

阶段结果

仓库当前版本为 MVP 1.9：支持订单问题、住宿服务、投诉体验、票据申请等对话式工单流程；SQLite 演示持久化，具备归属校验、幂等创建和状态历史。尚未接入真实 PMS / OTA / CRM。

01 / 产品判断

先确定信息从哪里来、谁有权处理，再决定是否调用模型。

项目的核心不是把所有问题交给 LLM，而是先识别任务性质和数据权限。相同的“房间”问题，可能是公共设施咨询、个人订单权益查询、现场维修请求，或对卫生状况的投诉。

  • 公共知识：入住政策、早餐、停车、设施等，从当前门店有效知识中检索。
  • 个人订单：房型、日期、权益和订单异常，必须经过演示身份认证并由 BookingService 校验订单归属。
  • 动态数据：实时房态、库存和车位不能由静态 FAQ 推断；当前原型提示人工核实。
  • 服务执行：维修、清洁、投诉、退款申请和发票需求，先补齐信息并复述确认，再创建本地演示工单。
  • 风险事项：安全事件优先级高于普通服务流程，触发专门安全指引与人工升级。
PRODUCT PRINCIPLE

模型负责理解与表达，确定性规则负责权限、业务边界和状态迁移；没有证据不猜测，没有确认不建单，没有外部系统就不声称已经执行。

02A / 产品决策记录

关键取舍：把模型的语义理解能力与业务授权、状态控制分开。

问题产品决策理由与边界
公共政策与个人订单混杂RAG 与 BookingService 分离公共知识可检索；个人订单事实必须经过身份认证和订单归属校验。
用户表达含糊规则优先，LLM 辅助解释模型只辅助理解，不授予权限，不直接决定交易动作。
多订单连续操作Context Manager 管理候选订单与当前操作防止沿用上一笔订单；订单选择和操作状态需要显式关联。
退款、维修、投诉、开票补充信息、复述确认后建单拒绝或未确认不创建工单；工单登记不等于退款、派单或开票执行。
工单分类容易混维度category / issue_type / issue_location / handling_channel 解耦业务责任、具体问题、发生地点和后续处理渠道分别表达。

以上决策依据当前仓库文档与代码整理；“演示身份认证”不是生产级认证，工单数据为本地 SQLite 演示数据。

03 / 版本演进

每次版本升级都对应一个明确的业务复杂度，而不是简单堆叠功能。

MVP 1.0

最小 RAG 问答

搭建 Streamlit 对话入口与模拟门店知识库，验证住宿 FAQ 的检索与回答链路。

能力：知识检索 · 基础问答
MVP 1.1

回答边界与知识约束

补充证据不足、未配置服务、动态房态和安全问题的兜底规则，区分通用知识与订单专属问题，避免 FAQ 越权回答。

能力：证据阈值 · 人工兜底 · 风险分流
MVP 1.2

混合意图识别与确定性路由

引入规则与可选 LLM 结构化分类、确定性业务路由、多轮上下文线索；建立 E001–E078 共 78 条合成路由案例与 CI 流程。针对房型变更表达、政策咨询与明确执行请求持续补齐边界。

关键变化：从“检索问答”转为“先判断任务，再选择处理路径”
MVP 1.3

身份认证与订单只读服务

引入合成订单数据、演示身份认证、BookingService、订单归属校验与审计事件；将个人订单事实从公共知识库中分离。

能力：身份边界 · 订单权限 · 只读服务
MVP 1.3.1

订单能力接入对话入口

把订单只读查询接入住客对话流程，使订单服务从独立模块成为可由对话编排调用的业务能力。

能力：对话编排 · 服务调用
MVP 1.4

订单列表、选择与多轮上下文

支持订单列表与候选订单选择，识别“我的入住 / 早餐 / 停车”等订单语义；订单异常转人工，并用 BookingService 返回字段约束回复。

关键变化：从单轮订单查询转为带上下文的订单服务
MVP 1.5

取消 / 退款与订单异常流程

区分取消政策咨询和明确取消 / 退款请求；多订单场景先选订单，核对订单级政策，执行前要求明确确认；订单错误关联具体订单后再收集问题并升级。

能力：订单级政策 · 显式确认 · 交易边界
MVP 1.6

多订单、多操作状态管理

修复单一 active_booking_id 残留造成的跨订单误复用；以 current_operation 管理当前任务，以 booking_operations 记录同一会话中的多笔操作，每笔操作独立关联订单、确认状态和演示处理结果。

关键变化：会话状态从“当前订单”升级为“多任务状态管理”
1.7

未单独形成可核实的发布节点

当前仓库版本记录未将 1.7 列为独立发布版本；对话行为识别、历史指代与上下文澄清能力在后续 1.9 能力中体现，不将其单独计作已发布版本。

版本记录说明：避免补造版本节点
MVP 1.8

本地服务工单生命周期

把退款确认后的演示登记扩展为 TicketService；SQLite 持久化，支持创建、查询、列表、指派、状态更新、状态历史、幂等创建与合法状态流转，住客可查看工单进度。

能力：SUBMITTED → ASSIGNED → PROCESSING → PENDING_USER → RESOLVED → CLOSED；支持升级与未解决重开
MVP 1.9

MECE 工单分类与对话式建单

把工单从单一退款场景扩展到订单问题、住宿服务、投诉体验、票据财务及咨询其他。住客描述问题后，系统识别订单、补充必要信息、复述确认，再自动创建本地演示工单；新增 category、issue_type、issue_location、handling_channel、priority 等分层字段。

当前仓库最新版本 · 对话自动建单 · 分类维度解耦 · 人工处理工作台

04A / 质量评测体系

把测试从“能不能运行”扩展为任务、可信度、风险和迭代四个层次。

  • 任务完成：意图分类、路由选择、订单选择、多轮状态和工单流程是否符合预期。
  • 信息可信：RAG 是否返回有效依据，订单回答是否只使用 BookingService 返回字段，工单信息是否完整。
  • 风险受控：未认证不得读取订单、未确认不得建单、跨住客不可读取工单、非法状态迁移必须拒绝。
  • 持续迭代：将错误按分类、上下文、权限、流程和输出归因，新增回归案例并对照版本验证。

当前已核实的自动化证据：11 个 Python 测试文件；2026-11-09 主分支 CI 成功，包含 pytest、RAG evaluation、routing regression 和 hybrid routing evaluation。仓库文件数不等于测试用例数；本页不声称测试总条数或线上准确率。

05 / 后续规划

下一阶段重点不是继续加意图，而是补齐真实系统接入与运营控制面。

2.0 · 系统集成

外部业务系统 Adapter

定义 PMS / OTA 订单与房态、CRM 客户档案、真实工单系统的接口契约；统一身份映射、数据权限、幂等键、超时与失败补偿。先只读接入，再逐步开放经授权的写操作。

2.1 · 运营控制

员工工作台与服务协同

引入生产级 RBAC、门店 / 员工 / 工单权限、派单与升级规则、消息通知、SLA 计时和审计日志；明确 AI 建议与员工实际执行的责任边界。

2.2 · 质量与规模化

可观测性与多门店运营

建立意图路由、检索命中、自动解决率、人工接管率、工单处理时长、重开率和用户反馈等指标；增加脱敏日志、回放评测、门店知识版本管理与多门店配置。

PRODUCT PHILOSOPHY

先定义业务边界，再分配模型与规则的职责；先把任务状态和责任主体管理清楚，再谈自动化比例；每一次自动化都必须能解释依据、确认动作并追踪结果。
