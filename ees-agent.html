02 / 独立应用原型 · 酒旅服务

EES 民宿客服
知识助手

住客问的看似都是住宿问题，背后却有不同的信息权限与处理边界。这个项目从民宿客服场景出发，验证 AI 如何基于有效知识回答，并识别何时不能猜测、必须查询订单或转交人工。

业务场景酒店 / 民宿住客咨询
产品形态RAG 知识问答 MVP
技术实现Python · Streamlit
当前状态MVP1 已搭建 · MVP1.1 迭代中
01 / 业务问题

客服问题的关键不只是“问什么”，还包括“这个问题应该从哪里获得答案”。

例如，“停车场在哪里”通常可以从门店知识库回答；“我预订的房型有停车位吗”则需要先识别订单上下文，不能用通用 FAQ 替代个人订单信息。实时房态、退款执行和安全风险也有各自不同的处理要求。

  • 通用知识：入住 / 退房时间、设施、停车、早餐等，可由当前门店有效知识支持。
  • 订单专属：用户自己的房型、入住日期、订单权益等，需要订单系统或人工核实。
  • 动态信息：实时房态、剩余房型和可售库存不能从静态 FAQ 推断。
  • 高风险事项：燃气、起火、电气危险等必须优先执行安全指引，不以普通问答方式处理。
02 / 产品决策

先判断问题类型与信息权限，再决定检索、回答或退出自动化。

INPUT住客问题文本与上下文
CLASSIFY问题边界FAQ / 订单 / 动态 / 风险
RETRIEVE知识检索门店与有效状态过滤
DECIDE证据与动作回答 / 核实 / 转人工
RESPOND受控回复引用依据与说明限制
  • 知识隔离：只检索匹配门店且状态有效的知识条目，减少跨门店和过期知识误用。
  • 证据阈值：检索结果不足时不生成确定性答案，明确告知需要人工核实。
  • 订单边界：“我预订的是什么房型”属于订单专属问题；MVP 未连接 PMS / OTA 时必须说明无法读取，不得从通用知识推断。
  • 动态与安全：实时房态、未配置服务和高风险问题走专门的兜底路径。
03 / 实现

把产品边界落实为可运行的检索与决策逻辑。

RAG MVPStreamlit 问答界面与模拟知识库
规则分流订单、房态、风险与证据不足处理
测试资产R01–R22 场景集、pytest、GitHub Actions

代码按界面、知识检索、问答决策和评测模块拆分。回答结果包含 grounded、needs_human、action、reason 与 sources 等字段，便于解释系统为什么回答、为什么拒答或为什么转人工。

当前仓库使用模拟门店 DEMO-HOMESTAY-001 与模拟政策。LLM 仅在存在知识依据时可选用于受控改写；当前不连接真实订单、PMS / OTA，不查询实时房态，不执行退款、工单或真实消息发送。

04 / 评测与质量

测试不只检查答案是否正确，也检查系统有没有做不该做的事。

已建立 R01–R22 场景集，覆盖常规知识命中、退款与改期、实时房态、订单专属房型、未配置服务及安全问题；测试关注知识条目命中、动作选择、人工升级与信息边界。

  • 常规 FAQ：检查门店和知识状态过滤、预期知识命中。
  • 订单专属问题：检查是否阻断通用 FAQ 检索并明确说明系统无订单读取能力。
  • 动态房态：检查是否避免将静态知识误作实时库存。
  • 安全问题：检查是否触发安全指引与风险兜底。

已配置 pytest 与 GitHub Actions。2026-10-30 最近一次工作流运行在本次资料核对时仍处于 queued 状态；此前有失败运行记录，因此这里不宣称测试集全部通过。应以最新 CI 结果为准。

05 / 产品复盘

RAG 产品的可靠性，不只取决于“检索到什么”，也取决于“什么问题不应该检索”。

本项目最重要的产品判断，是将问题类型、数据权限、知识有效性和风险等级纳入回答前的决策流程。订单查询不是一个更聪明的 FAQ，而是需要身份与订单上下文、权限校验及外部系统连接的另一条业务链路。
