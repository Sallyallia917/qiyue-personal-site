02 / 独立原型 · 营销决策

Coffee Growth
Engine

把消费者研究转成可以执行、可以测试的会员营销决策。规则负责商业约束，大模型负责适合生成式 AI 的语言任务——先让系统可控，再逐步扩展。

业务场景精品咖啡会员复购
研究基础消费者满意度研究
当前重点规则模块与质量评估
项目性质独立原型 / 非生产系统
01 / 观察

营销不是发券，而是对人、商品、成本和时机做判断。

消费者满意度研究为产品、服务、品牌与感知价值提供了业务观察角度。它能帮助提出营销假设，但不能直接证明某项策略一定提升复购；因此，我把研究洞察当作决策设计的起点，而不是直接当作算法结论。

  • 用户：会员处于什么状态，是否有营销授权？
  • 商品：推荐是否匹配偏好，库存与成本信息是否完整？
  • 活动：优惠是否超预算，折后毛利是否仍然合理？
  • 评估：系统是否能在异常输入下拒绝不合理方案，并给出可解释原因？
02 / 建构

规则先决策，模型后表达；商业底线不能交给生成结果决定。

INPUT会员 / 商品结构化业务数据
SEGMENT会员分群授权与购买状态
SELECT商品推荐偏好与可售性
GUARDRAIL预算 / 毛利约束与边界检查
NEXT文案 / 评估生成、测试与反馈
  • 会员分群：按会员状态识别可触达对象，并将未授权人群排除在营销之外。
  • 商品推荐：过滤库存、价格与成本异常的候选商品，再根据偏好匹配等规则排序。
  • 优惠校验：检查预算、门槛、核销假设和折后毛利等业务约束。
  • 模型边界：规划由 LLM 生成营销文案，但不让模型绕过分群、预算与毛利硬约束。
03 / 实现

把业务规则写成模块，再用测试暴露边界问题。

规则模块分群、推荐、优惠约束
单元测试覆盖典型输入与边界条件
评估迭代从正常样例扩展到失败场景

项目使用 Python 组织业务逻辑，并围绕正常路径、边界输入和不合法活动设计测试。当前重点从“能生成一个结果”转向“错误输入是否会被识别、商业约束是否会被执行、失败是否能被定位”。

工程状态说明：此前阶段记录为功能分支单元测试 51 项通过；质量评估 MVP 的 8 个案例中，仅正常案例通过，其余边界或故障案例仍需修复。该状态不等于端到端系统已通过验证，正式发布前应重新运行并更新结果。

04 / 表达

产品价值不在“用了大模型”，而在把商业判断做成可检查的行为。

  • 把消费者研究转成待验证的会员运营假设。
  • 把业务约束拆成独立规则，降低营销决策对自由生成的依赖。
  • 把评估从单一正常样例扩展到预算超限、无效商品、优惠券不匹配、输出结构错误与 API 故障等场景。
  • 将下一阶段目标定义为可重复的端到端活动生成与质量报告，而非提前宣称复购或营收提升。
关键取舍

先建立确定性约束和失败可见性，再扩展模型生成能力；先证明方案能被正确执行，再讨论业务效果。

05 / 下一轮

从“规则能跑”走向“营销决策可评估”。

  • 修复硬门槛：优先解决受众边界、预算、无效商品、优惠券匹配、结构化输出与 API 失败处理。
  • 补齐端到端流程：让输入数据、决策结果、生成文案和评估报告形成可复现链路。
  • 建立评测集：保留案例输入、预期行为、硬约束、失败类型与修复记录。
  • 最后验证业务价值：在有真实数据与合适对照设计后，再评估触达、核销、毛利与复购指标。
